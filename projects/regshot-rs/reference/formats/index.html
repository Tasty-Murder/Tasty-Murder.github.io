    Formats¶

    .rshot — the native snapshot format¶

    An 8-byte header (the magic RSHOT, a format version byte, a compression flag, and a reserved byte), followed by one rkyv-archived payload holding the metadata, the snapshot's own name/path tables, its keys and values, and the deduplicated value data. regshot writes the payload as a single zstd frame. Reading validates the archive before using it, since a .rshot file is untrusted input. After zstd decompression, loading is rkyv's archived access followed by re-interning each name and path into the session, so the same path loaded from two files shares one identity. Splitting the payload into separately compressed sections is a possible future layout change, which would get a new version byte.

    Version Contents
    1 Metadata, names, paths, keys, values, and value data
    2 Version 1's payload unchanged, plus the recorded environment (below)
    3 Version 2's payload unchanged, plus the current control set (below)
    4 (written today) Version 3's payload unchanged, plus each key's last write time

    This build reads all four. Older files just lack what later versions added.

    Recorded environment. At capture, regshot shot (and the MCP take_snapshot tool) records the value of each environment variable that the snapshot's REG_EXPAND_SZ values reference with %NAME%. It records only those variables, never the capturing process's whole environment, which routinely holds unrelated credentials. That's enough to show every REG_EXPAND_SZ value expanded later, on any machine, exactly as it would have expanded on the captured one. regshot info lists what a snapshot recorded.

    Current control set. HKLM\SYSTEM\CurrentControlSet is a link to one of the ControlSetNNN keys, the one SYSTEM\Select\Current names. A snapshot holds that control set once, under the name CurrentControlSet, and records which ControlSetNNN it was. Other control sets keep their own names. CurrentControlSet is the name that's correct on every machine, which matters when an undo or installer script is replayed elsewhere. If two compared snapshots recorded different control sets (after a Last Known Good boot, say), regshot diff notes it. regshot info shows the recorded one.

    Architecture-independent by construction: a .rshot written by the x86 build is byte-identical to one written by the x64 or ARM64 build from the same input — fixed-width little-endian fields throughout, no usize on the wire — which is what makes it safe to compare snapshots captured on different machines with different builds.

    Legacy .hiv / .hivu import¶

    Upstream's two incompatible formats (ANSI .hiv, Unicode .hivu) are readable for migration, not writable:

    regshot import-hive old.hiv  --out new.rshot   # ANSI,    1.8.x / 1.9.x
regshot import-hive old.hivu --out new.rshot   # Unicode, 1.9.x

    Both formats carry a filesystem-entry chain alongside the registry data (addressed by its own offset in the file header, independent of the registry sections), which the importer walks and discards, reporting the count of dropped entries rather than silently losing them — regshot-rs is registry-only. Imported snapshots are tagged with an Unknown WOW64 view, since upstream predates that distinction. Upstream followed the CurrentControlSet link, so its files hold the current control set twice; the import keeps one copy, as described above.

    .reg (v4 / v5)¶

    REGEDIT4 (ANSI) and Windows Registry Editor Version 5.00 (Unicode, UTF-16LE with BOM). See Undo scripts and installers for the WOW64-view caveat that applies to this format specifically.

    JSON / NDJSON¶

    json emits a structured timeline for tooling. It's the same report model the HTML page embeds.

    ndjson-ecs (regshot diff --template ndjson-ecs) emits one Elastic Common Schema 9.5 event per change, one JSON object per line, ready for a SIEM ingest pipeline:

    Field Value
    @timestamp When the "to" snapshot was captured (omitted if it recorded no time)
    event.kind / event.category / event.type event / ["registry"] / ["creation"], ["deletion"] or ["change"]
    event.action key-added, key-deleted, value-added, value-deleted, value-modified
    event.module / event.dataset regshot / regshot.diff
    registry.hive, .key, .path, .value e.g. HKLM, SOFTWARE\Foo, HKLM\SOFTWARE\Foo\Bar, Bar
    registry.data.type REG_SZ, REG_DWORD, …
    registry.data.strings String types decoded (one entry per REG_MULTI_SZ item); DWORD/QWORD as decimal
    registry.data.bytes Base64, for every other type
    host.name / user.name From the "to" snapshot, when recorded
    regshot.category, .view, .interesting, .transition, .previous.data The change category, WOW64 view, known-interesting rule, snapshot pair, and a modification's old value

    registry.data is the value after the change, or the last value before a deletion. --generalize and --only-interesting apply as they do to the report. String data is carried only as strings, never also as bytes, because raw bytes would bring back the per-user paths that generalization removes. The MCP generate_report tool accepts ndjson-ecs too.
