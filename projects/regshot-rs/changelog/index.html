    Changelog¶

    This page tracks what's actually implemented, not just planned — see the repository's CHANGELOG.md-equivalent (GitHub Releases) for the canonical, versioned record once tagged releases exist.

    Unreleased¶

    Implemented and tested¶

    • Core data model (regshot-core): interned, WOW64-view-rooted PathId/NameId, immutable sorted Snapshot/KeyEntry/ValueEntry, content-addressed BlobStore.
    • N-way diff engine: the TimelineMatrix merge-join, all five change categories, a brute-force reference oracle, and a proptest property suite covering reflexivity, the undo-restores-prior-state property, N-way/pairwise consistency, category disjointness, and WOW64-view non-aliasing.
    • The .rshot on-disk format: rkyv-archived, zstd-compressed, magic/version header, with a decompression-bomb guard.
    • Capture trait boundary (regshot-core::capture, regshot-capture): the RegistrySource/KeySink traits, a tested SyntheticSource used by every test on every platform, and — Windows only — the real Win32 backend (RegEnumKeyExW/RegEnumValueW, explicit KEY_WOW64_64KEY/KEY_WOW64_32KEY).
    • Legacy .hiv/.hivu import: reads upstream Regshot's ANSI and Unicode snapshot formats, reverse-engineered from upstream's own source (see regshot-core::legacy's module doc), including the ANSI→UTF-16LE value-data conversion needed to preserve this project's storage invariant and cycle-safe iterative tree walking upstream's own loader never bothered with.
    • Output emitters (regshot-report): txt/json/html report templates via minijinja (html embeds the report as JSON and renders it with hand-written vanilla JS — virtualized timeline/pairwise table, search, category/kind/view facets, a detail panel with prefix/suffix diff highlighting, dual light/dark theme using the exact palette in docs/guide/reading-the-report.md), hand-written reg4/reg5/ps1 undo-redo script renderers (with the mixed-WOW64-view refusal for .reg, and a header comment naming the view and the reg.exe /reg:32//reg:64 invocation needed to import it correctly — reg4 is REGEDIT4/ANSI, upstream Regshot's own format; non-Latin-1 REG_SZ text falls back to hex(1): with the raw UTF-16LE bytes rather than losing data, lossless on any NT-based Windows), and the regshot query/MCP query_changes filter expression language (category/path/name/view/kind/data/snapshot fields; ==, !=, starts_with, contains, in (…), &&/||). ReportChange now also carries rendered before/after value text (from_data/to_data), which json and html show; txt deliberately doesn't, to stay byte-comparable with upstream 1.9.1's plain-text output.
    • Installer-script templates (regshot-report::installer): nsis and inno render one script holding both an installer (replays the diff by default; --direction undo swaps) and an uninstaller (its exact reverse). Both handle mixed-WOW64-view changesets natively: NSIS through SetRegView, Inno through HKLM64/HKLM32 roots. Inno's uninstaller restores values through RegSetValueExW from generated [Code], because [Registry]'s uninsdelete* flags can't restore modified or deleted values and RegWriteBinaryValue corrupts bytes ≥ 0x80 via the ANSI codepage. Anything a format can't express exactly is refused with a list of the offending entries, never dropped. unl writes Regshot-Advanced's removal-list format. All three are also available through the MCP export tool. Windows CI compiles the nsis/inno output with the real toolchains and round-trips it against a live registry in both views — see docs/guide/undo-and-installers.md.
    • CI on every architecture and the MSRV: the Windows job now builds and tests on x64, 32-bit x86 (running under WOW64) and native ARM64 runners. A new MSRV job checks that the workspace builds on its minimum Rust version and regshot-gui on 1.95. It found the declared minimum of 1.85 was wrong (dependencies need 1.88), so the workspace now declares 1.88. The new x86 leg also found that the 32-bit build had never compiled: the .rshot decompression cap was 4 GiB as a usize. It's now 1 GiB on 32-bit targets, so the i686 release artifact builds.
    • Fuzzing: cargo-fuzz targets for .rshot reading, .hiv/.hivu import, the filter language and regshot.ini migration. The two file-format targets also check a write-and-read round trip, and they start from generated valid seeds. CI fuzzes each target for 30 s on every PR and for 10 min daily with a persisted corpus. See docs/development/contributing.md.
    • GUI reads the settings file: the settings model moves out of the CLI into a new regshot-config crate shared by both interfaces. The GUI now starts from [capture] (hives, views, skip and whitelist) and [report] generalize_paths, and says so in the status bar when it falls back to a default.
    • Start menu: regshot tui with no snapshots shows a menu instead of an error. It can open snapshots here in the explorer, take a snapshot (Windows), compare to an HTML report, export a script or installer, import a .hiv, show a snapshot's details, reopen a triaged set, or open the GUI or the settings file. Nothing loads until you choose, each item shows its equivalent command, and every action runs through the same code as that command. With no terminal attached it prints the help and exits 2. A bare regshot always prints the help and exits 2: a subcommand is required, so a script can never land in an interactive session by accident.
    • TUI timeline view and fuzzy search: s toggles the change table between pairwise and a timeline of every change across all snapshots, with one state glyph per snapshot. / is now a ranked fuzzy search (nucleo), and n/N step through matches best first. The table gains a view column, so a 64-bit entry and its 32-bit namesake no longer look like one row listed twice. The TUI guide is rewritten from the real behavior; it still described the TUI as unimplemented.
    • TUI triage persistence: marks are saved as you make them to a .regshot-triage-<hash>.json sidecar next to the snapshots, keyed by their contents and order. V jumps to the next untriaged change, X, X clears all marks (it used to be a single V), and the facets pane shows the triaged count. regshot query --triaged only|exclude filters by the same marks.
    • Shell completions and man pages: regshot completion <bash|zsh|fish|powershell|elvish> prints a completion script and regshot man --out-dir <dir> writes regshot.1 plus a page per subcommand, both generated from the clap definition itself. Release archives now include both, under completions/ and man/. See docs/getting-started/installation.md.
    • ndjson-ecs output (regshot diff --template ndjson-ecs, MCP generate_report): one ECS 9.5 registry event per change. Values carry typed registry.data: decoded strings, decimal numbers, or base64 bytes. Custom regshot.* fields hold the category, view, interesting rule, snapshot pair and previous value. See docs/reference/formats.md.
    • Known-interesting heuristics fixes: per-user rules now match under every HKU\<SID>\ user hive, not just HKCU. Captures default to HKLM + HKU, so a per-user Run entry was going unflagged. A prefix rule also no longer matches a sibling that merely shares its prefix: …\RunOnce was being labeled Run.
    • The GUI (regshot-gui, egui/eframe): a desktop shell with a snapshot list (open .rshot, import .hiv/.hivu, reorder, details), capture on Windows with live progress, Compare (renders the HTML report and opens it), and Export (every script template). It goes through the same library paths as the CLI, uses the shared palette (regshot-report::palette, which a test keeps in step with the report's CSS), and is covered by headless egui_kittest UI tests. See docs/guide/gui.md.
    • Shared script rendering (regshot-report::script): the CLI export, the MCP export tool and the GUI render and encode scripts through one render_script. ps1 scripts are now written with a UTF-8 BOM. Before this they were BOM-less, and Windows PowerShell 5.1 reads such scripts in the system ANSI code page, corrupting any non-ASCII key name or value an undo script restores.
    • View-mismatch check everywhere: query, export and tui now refuse snapshots captured with different WOW64 view sets, as diff always did, and gain the same --allow-view-mismatch override. So do the MCP diff, suggest_interesting, query_changes, generate_report and export tools, which previously skipped the check entirely (allow_view_mismatch: true to override). An export across mismatched sets would have produced an undo script that deletes every entry in the view only one side captured. The check lives in regshot_core::check_view_sets.
    • REG_EXPAND_SZ expanded form: capture records the value of each environment variable the snapshot's REG_EXPAND_SZ values reference. It never records the whole environment, which often holds credentials. This is stored in .rshot format v2, and version-1 files still load. The report (json from_expanded/to_expanded, and the HTML detail panel), the TUI and MCP get_value_data show each value expanded with ExpandEnvironmentStrings semantics, and list any variable that wasn't set at capture. regshot info lists what was recorded.
    • HTML report deep links, hex dump, and (NULL!): the URL hash mirrors the whole view (mode, search, facets, selected row), with a Copy link button, and opening or pasting a link restores that view. The selection now stays on the same row across filter changes. Byte-list values get a hex dump with differing bytes marked, and each side shows its size. A present-but-zero-length value shows upstream's (NULL!), using the new from_size/to_size byte counts on ReportChange, which the json output carries too. The timeline also no longer merges a 64-bit value with its 32-bit namesake into a single row. Headless-browser tests cover all of it.
    • Known-interesting-location heuristics (regshot-report::interesting): a curated table (Run/RunOnce, services, scheduled tasks, AppInit_DLLs, Image File Execution Options, Winlogon, LSA packages, shell extensions) matched on (hive, path) — deliberately not on WOW64 view, since a redirected path reads identically through both views and a view-restricted rule would miss every 32-bit installer's entry. Surfaced via ReportChange's new interesting field, a ⚠ badge/facet/detail-panel entry in the HTML report, regshot diff --only-interesting (narrows the report and recomputes its summary counts), and the MCP suggest_interesting tool (findings grouped by rule, ranked by count).
    • Path generalization (regshot-report::generalize): regshot diff --generalize rewrites C:\Users\<name>\AppData\{Roaming,Local}\… to %AppData%/%LocalAppData% (any drive letter) and collapses a per-user SID under HKU\S-1-5-21-… to HKU\<user>, applied to the report's path/from_data/to_data only — never the underlying .rshot data. Defaults to [report] generalize_paths (itself true by default); --no-generalize overrides it in either direction, unlike --allow-capture's OR-only merge, since this flag pair is properly negatable.
    • REG_EXPAND_SZ readable text (report_value_text): the report (txt/json/html) and query's data field now decode REG_EXPAND_SZ the same way as REG_SZ, instead of the hex(2):… byte list every other non-REG_SZ/REG_DWORD type falls back to. reg4/reg5 export is deliberately unchanged (reg_value_literal, still hex(2):…) — that's what real regedit.exe itself writes for REG_EXPAND_SZ, since .reg's quoted-string syntax has no way to mark a value as expandable. --generalize picks this up automatically, since it operates on whatever quoted text the report renders.
    • The TUI (regshot-tui): a ratatui interactive explorer — windowed table over the timeline (never renders more than the visible viewport regardless of dataset size), snapshot rail, facets pane, detail pane, vim-native keybindings, tested via insta frame snapshots against synthetic data.
    • regshot config: TOML config file (--init), and a migration reader for upstream's regshot.ini (--migrate) that handles both upstream's and Regshot-Advanced's incompatible [SkipRegKey] dialects, with filesystem-related keys surfaced as warnings rather than silently dropped. Read back in as per-command defaults by shot/diff/mcp, CLI flags still taking precedence — see docs/reference/configuration.md for the exact merge per field.
    • MCP server (regshot-mcp), both transports: load_snapshot, take_snapshot (live capture, Windows-only, gated behind --allow-capture, sharing its orchestration — regshot-capture::capture_snapshot — with regshot shot so the two entry points can't drift apart on what "capture" means), list_snapshots, diff (per-transition category counts, never row-level detail), query_changes (the filter language above), suggest_interesting (the known-interesting heuristics above, grouped findings), get_value_data, describe_filter_syntax, generate_report (txt/json/html), and export (reg4/reg5/ps1/unl/nsis/inno) — 27 tests exercising every tool through the real JSON-RPC protocol. The streamable HTTP transport (--http host:port) is loopback-only unless --allow-non-loopback, requires a locally-generated, persisted bearer token unless --no-auth (itself refused on a non-loopback bind), and relies on rmcp's own Host-header allowlist as the DNS-rebinding mitigation — see docs/guide/mcp-server.md's security model. Run by hand in a terminal, the stdio server says what it is and prints the claude mcp add/codex mcp add lines to register it, instead of looking hung; Ctrl-D before any client connects exits cleanly. --http prints a ready-to-paste connect command. The server identifies itself as regshot-rs in the MCP handshake (it previously reported the SDK's own name, rmcp). The README has config examples for Claude Code, Codex, opencode, Cursor, VS Code and Gemini CLI, and the guide shows how to keep the HTTP server running as a Task Scheduler task or a systemd user unit.
    • CLI surface (regshot-cli): the full command shape from the reference parses today, and every subcommand is wired to a real backend except shot, which needs the live Windows registry and only runs on that platform.

    • Full workspace lint posture (unsafe_code denied outside the Win32 FFI boundary, unwrap/expect/panic/indexing denied in library code), CI covering fmt/clippy/test/doc on Linux and a build+test smoke check on Windows x64.

    • Localization groundwork (regshot-i18n): every human-facing string in the GUI, start menu, explorer, command-line messages, and the txt/html reports is a Fluent message in locales/en.ftl. Machine output (JSON, NDJSON, CSV, scripts) is not translated. The language comes from --lang/REGSHOT_LANG, the settings file's new [ui] language, or the system, and falls back to English.

    • Plurals follow each language's CLDR rules, including those the HTML report's script counts in the browser.
    • Terminal columns are padded by display width, so double-width CJK labels line up.
    • The HTML report sets lang/dir and uses logical CSS properties, so right-to-left languages lay out mirrored.
    • Tests check that every message ID in the sources exists, that every message is used, and that translations use the same placeables as English.
    • regshot info now shows the capture time as a date instead of raw milliseconds (--json keeps the milliseconds).
    • 36 languages: every one of the 29 in upstream Regshot's language.ini, plus Korean, Arabic, Vietnamese, Indonesian, Romanian, Finnish and European Portuguese. Strings that mean the same in both programs come from upstream's human translators, credited in each file, and a test checks them against a vendored language.ini, decoding each section with the codepage it was written in (GBK, Big5, Shift-JIS, windows-125x). Where upstream was damaged or wrong (characters lost to cp1251, keyboard "keys" for registry keys), the fix and its reason are recorded. The rest is machine-translated and marked as such. A completeness test keeps every shipped language at every message.
    • regshot config --migrate carries upstream's [Setup] Language= into [ui] language.
    • System tags map to the shipped variant: zh-HK→zh-TW, nn→nb, sr→sr-Latn, pt→pt-BR.

    • See docs/development/translating.md for the language list.

    • GUI redesign: the window draws itself the same on Windows and Linux instead of following each platform's defaults.

    • Bundled fonts: Inter for text, JetBrains Mono for paths and values, and Phosphor icons.
    • Design tokens from the report's palette, a 4-point spacing grid and a small type scale.
    • Cards with radii matched to their controls, and a toolbar, sidebar and status bar.
    • Snapshot rows show the label, capture time, views and counts at a glance.
    • Screenshots in the GUI guide are rendered by an ignored test (cargo test -p regshot-gui --test screenshots -- --ignored).
    • Every language in the GUI:
    • Chinese, Japanese and Korean use bundled Noto Sans SC/TC/JP/KR, cut down to the characters the translations use. The interface language's own regional font comes first, so a character shared by several gets that language's form. A test fails when a translation gains a character its font lacks, and crates/regshot-gui/assets/fonts/subset.sh rebuilds the fonts.
    • Hebrew and Arabic read right to left. egui shapes Arabic letters but has no bidirectional layout, so the GUI runs the Unicode bidi algorithm itself: runs come out in visual order, numbers and Latin text keep their own direction, and brackets mirror. The whole window mirrors too: the sidebar moves to the right, and labels, rows and buttons start from the right. Long text is cut at its logical end.

    • Known gap: right-to-left text typed into a text field shows its words in typing order.

    • Faster capture. Everything a capture does besides calling the registry is about 5× faster: walking, interning and building a 106k-key, 161k-value tree went from 415 ms to 77 ms (cargo bench -p regshot-capture).

    • The walk passes each key's interned path down to its values and subkeys instead of building and re-parsing full path strings.
    • Names live in one arena, looked up by the hash of their folded form, and are folded without allocating when they're ASCII. Value data is deduplicated into one buffer.
    • One set of buffers serves the whole walk, so a key or value costs no allocation of its own.
    • The walk is written once against a small RawRegistry trait. The Win32 backend and the in-memory test registry both implement it, so tests and benchmarks run the real walk on any platform.
    • Skip and whitelist patterns fixed and faster. Patterns are compiled once and matched without building paths, and a skipped key's subtree is no longer read at all.
    • Fixed: a path with a hive, like the documented --whitelist-key 'HKLM\SOFTWARE\MyApp', never matched, so that example captured nothing. Paths now match with a short or long hive name, or without one to match under any hive.

    • Changed: a pattern no longer matches as a substring (Temp used to skip Attempt). As in upstream Regshot, it names whole keys: a path, or a key name anywhere.

    • Native capture where it's exact. Capture reads the registry through ntdll (NtOpenKeyEx, NtEnumerateKey, NtEnumerateValueKey, NtQueryKey) wherever that reads a view exactly as the Reg* API does, and through the Reg* API elsewhere.

    • The native calls see the physical tree. In a 64-bit process that's the 64-bit view, because the Reg* layer, not the kernel, redirects 32-bit-view opens. Under WOW64 both views work.
    • Windows CI compares the two backends key for key, in every view, on x64, x86 and ARM64, and logs whole-hive timings for each.
    • One CurrentControlSet. A snapshot holds the current control set once, as CurrentControlSet, instead of twice (the link and the ControlSetNNN it points to). That's the name that's correct when a script is replayed on another machine. .hiv imports, which hold it twice, are reduced the same way.
    • The control set's number is recorded in .rshot format v3 (v1 and v2 still load), shown by regshot info, the GUI and the start menu.

    • regshot diff notes when compared snapshots recorded different control sets.

    • Parallel capture. Each hive is walked on every core: keys near the root, and the subkeys of wide keys, are read by rayon workers into compact logs, which are then replayed into the snapshot in exactly the single-threaded walk's order. The snapshot is the same however many threads read it (a test compares them entry for entry), and RAYON_NUM_THREADS caps the count. On a 4-core Windows CI runner, HKLM's 64-bit view (648k keys, 1.09M values) now takes about 15 s instead of 49 s, and its 32-bit view 5 s instead of 33 s.

    • Smaller registry calls. Each call is offered only the buffer size its key needs, not the largest the walk has needed so far: the cost of a call grows with the length it's given. That alone made the native walk of HKLM 2.9× faster (17 s instead of 49 s on one thread).

    • Fixed: the native walker's "open links as themselves" mode followed them anyway: it needs OBJ_OPENLINK, not REG_OPTION_OPEN_LINK. Capture doesn't use the mode yet.

    • Incremental capture (opt-in). regshot shot --baseline before.rshot reuses the baseline's values for every key whose last write time hasn't changed, instead of reading them again. Every key is still visited, and the snapshot is the same one a full capture produces (a test compares them). It's opt-in, because a program can forge a key's last write time to hide a change. If the current control set changed since the baseline, nothing under CurrentControlSet is reused.

    • Each key's last write time is now captured and stored: .rshot format v4 (v1–v3 still load).

    Dropped¶

    The differential test against the real Regshot.exe was dropped: it would need upstream's binary vendored and driven headlessly, for little gain over the existing format and diff tests.

    If a guide or reference page describes a flag or behavior that isn't in the list above yet, it's documenting the intended, stable shape — most subcommands' argument parsing is already final even where their backend isn't built.
