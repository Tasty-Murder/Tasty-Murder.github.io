    Reading the report¶

    The HTML report is a single self-contained file — inline CSS and JS, zero network requests, built for isolated analysis machines. It's designed to stay usable at real-world scale: a full registry diff routinely produces 100k–1M rows, so the report virtualizes rendering (only the rows actually visible in the viewport are ever materialized as DOM nodes) rather than choking the browser.

    Layout¶

    ┌────────────────────────────────────────────────────────────────────┐
│  regshot-rs · <label>            [Timeline ▸ Pairwise]   [⌕ search] │
├──────────────┬─────────────────────────────────────────────────────┤
│ SNAPSHOTS    │  Cat  Kind  View  Path                        Name   │
│ [0] before   │   ~   value  64   HKLM\…\Run\Updater           …     │
│ [1] after    │   +   key    32   HKLM\…\CurrentVersion\…            │
│              │                                                      │
│ FILTERS      │                                                      │
│ ☑ Keys       │                                                      │
│ ☑ Values     ├─────────────────────────────────────────────────────┤
│ CATEGORY     │  Path      HKLM\SOFTWARE\…\Run\Updater                │
│ ☑ KeyAdd 3   │  Category  VALMODI                                   │
│ ☑ ValModi 12 │  S2        "C:\ProgramData\upd.exe"                  │
│ VIEW         │  S3        "C:\ProgramData\upd.exe --silent"         │
│ ☑ 64  ☑ 32   │  (differing text highlighted)                        │
└──────────────┴─────────────────────────────────────────────────────┘
    • Timeline / pairwise toggle — see Comparing. Timeline reconstructs each entity's presence across every compared snapshot (not just consecutive pairs) entirely client-side from the same flat change list the pairwise view uses — no extra data needed.
    • Detail panel — click (or arrow-key to) a row to see its full path, category, and — for a value row — the rendered data on each side of the change, with the differing prefix/suffix highlighted. This is a bottom panel, not an inline expansion, so it doesn't complicate the fixed-height row math virtualization depends on.
    • View facet — filter to the 64-bit view, the 32-bit view, native, or unknown; see Registry views.
    • Search, facets, keyboard nav — instant client-side substring search over path and value name, facets by kind/category/view, and j/k/g/G///Esc navigation.
    • ⚠ Known-interesting — a ⚠ badge on any row matching the known-interesting-location heuristics (Run, Services, AppInit_DLLs, …), an "Only interesting" facet, and the matched rule name shown in the detail panel.
    • Deep links — see below.

    Deep links¶

    The URL's #hash always mirrors what you're looking at: timeline or pairwise, the search text, any facet you've turned off, and the selected row. Copy link copies it, and opening that link (or pasting a new hash into a report that's already open) restores exactly that view, with the selected row scrolled into sight and its detail panel open. The hash updates in place as you move around, so j/k and typing don't fill your back-button history.

    A link is identified by the row itself — its view, path, and value name, plus which transition in pairwise mode — not by its position, so it still points at the same change if you open it with different filters. A link to a row that isn't in the report just opens with nothing selected.

    The link is the report file's own path plus the hash, so it only works for someone who has the same report file. Nothing about the view is sent anywhere, and opening a link still makes no network requests. The same goes for the selection generally: changing a filter keeps the selected row selected, or clears the selection if that row is filtered out, instead of jumping to whatever row now sits in the same position.

    Hash key Meaning
    m=p Pairwise mode (timeline is the default)
    q= Search text
    kind=, cat=, view= The facet values still enabled, comma-separated (present only when some are off)
    int=1 Only known-interesting rows
    sv=, sp=, sn= Selected row's view, path, and value name (sn absent for a key row, empty for a key's default value)
    at=<from>-<to> Selected row's transition, in pairwise mode

    Visual design¶

    The report's colors are a deliberate tribute to the original Regshot icon: black and white carry the layout, and the three logo-derived hues — blue, red, green — carry meaning only, never chrome. Every accent is contrast-checked against its own background (light and dark themes use different tints of the same hue, since the icon's raw blue fails contrast on white):

    Role Light theme Dark theme
    Accent / modified #0B6AAE #56B6F8 (the icon's own blue)
    Added #1F7A34 #5DD17A
    Deleted #B81919 #FF6B6B

    Color is never the only signal — every change also carries a glyph (+/−/~) and a distinct row treatment, since roughly 8% of men have a red/green color vision deficiency and a red/green diff is precisely the worst case for it.

    Value rendering¶

    REG_SZ/REG_EXPAND_SZ render as "…" and REG_DWORD as dword:…, and the detail panel highlights the differing prefix/suffix of that text between the two sides. Everything else (binary, REG_QWORD, REG_MULTI_SZ, REG_NONE, …) is a hex(N):… byte list, which the detail panel shows as a classic hex dump: offset, 16 bytes per line in hex, and the same bytes as ASCII. Every byte that differs from the same offset on the other side, including bytes one side has and the other doesn't, is marked in both columns. The dump stops after the first 4096 bytes and says how many more there are.

    Each side also shows its size in bytes. A value that exists but holds zero bytes shows upstream Regshot's (NULL!), which is different from (absent), a value that doesn't exist at that point. It's also different from an empty REG_SZ: that still holds its 2-byte NUL terminator, so it shows as "" with a size of 2. The JSON output carries the same sizes as from_size/to_size.

    REG_EXPAND_SZ renders as readable text here — genuinely different from what a reg4/reg5 export writes for the same value (hex(2):…, matching real regedit.exe's own .reg-export behavior, since the quoted-string syntax has no way to mark a value as expandable). A report is for reading, an export file is for reg.exe to import; each renders the value the way its own reader needs.

    Under a REG_EXPAND_SZ value, the detail panel also shows its expanded form, with every %VAR% resolved the way Windows' ExpandEnvironmentStrings would have resolved it on the captured machine. The values come from the environment the snapshot recorded at capture, not from the machine viewing the report. A variable that wasn't set at capture stays as %NAME%, as Windows leaves it, and is listed under "not set at capture". Snapshots written before environment recording existed, and legacy .hiv imports, have nothing to expand against, so they show only the stored form. --generalize applies to the expanded text too, because expanding %AppData% brings back the per-user path it exists to hide. The JSON output carries the same data as from_expanded/to_expanded, and the TUI's detail pane shows it too.
