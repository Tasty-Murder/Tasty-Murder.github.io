    regshot-rs¶

    Fast, N-snapshot Windows registry comparison. A modern Rust reimplementation of Regshot: registry only (no filesystem scanning), built around an N-way diff engine instead of the classic two-shot comparison, with a complete CLI, an interactive TUI, a self-contained HTML report, template-driven output, and an MCP server for agents.

    View on GitHub Getting started

    Early scaffolding

    This project is under active development. The core data model, interning, and N-way diff engine (regshot-core) are implemented and tested. The capture backend, report templates, TUI, GUI, and MCP server are being built out — see the changelog for exactly what works today, and the architecture page for how the pieces fit together.

    Why another Regshot¶

    Upstream Regshot compares exactly two snapshots at a time, using an O(n·m) nested-loop comparison over a mutable linked tree — a structural limit that has nothing to do with performance and everything to do with the data model: a match flag mutated in place during comparison simply cannot represent a third snapshot. regshot-rs starts from a different model: snapshots are immutable, flat, sorted arrays, and comparing any number of them is a single linear merge-join.

    • N snapshots, not two

      Compare a whole sequence — before, during, after, after-reboot — in one timeline, not a chain of two-shot diffs.

    • A real diff engine

      A merge-join over sorted, interned paths: linear in the number of entries, not quadratic.

    • CLI, TUI, and MCP — one engine

      Everything the TUI or a report template can do is reachable as a CLI flag or an MCP tool. Nothing is TUI-only.

    • x86, x64, and ARM64

      All three are Rust Tier 1 targets, built and tested natively in CI — including on windows-11-arm.

    The registry-only decision¶

    Upstream Regshot optionally scans a list of filesystem directories alongside the registry. regshot-rs deliberately does not: registry diffing and filesystem diffing are different problems that happened to share a report format, and cutting one lets the other get simpler and more correct everywhere it touches — one entity model, five change categories instead of eleven, one capture trait instead of two. See No filesystem scanning for the full reasoning and what to use instead.

    WOW64 views: the bug this tool is built to avoid¶

    On 64-bit Windows the registry has two views, and a 32-bit process's reads of e.g. HKLM\Software are silently redirected to HKLM\Software\Wow6432Node — no error, no warning. A 32-bit build and a 64-bit build of a naive registry differ capture different registries at the same path, and diffing one against the other produces a completely fabricated changeset. This is load-bearing enough that it is encoded in the type system, not left to a runtime check — see Registry views.
